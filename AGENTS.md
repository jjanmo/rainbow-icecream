# Rainbow Icecream — project conventions

Investment portfolio management app. Update this file as new conventions/decisions come up during work — don't wait to be asked.

## Stack (non-negotiable)
Next.js 16 **Pages Router** (never App Router) · Supabase (Postgres + Auth) · Toss 증권 Open API · shadcn/ui "base-nova" (built on **Base UI**, not Radix — verify via no `radix-ui` deps) + Tailwind · TanStack Query for all server state · TypeScript · pnpm · Recharts · dnd-kit (reordering role/sector categories — the "축 관리" modal and the role bucket cards on `/portfolio`, ADR-0063 — not for holding assignment, see below).
- **dnd-kit was removed then reintroduced** — ADR-0062 dropped it because `/portfolio`'s role/sector classification no longer uses drag-and-drop (it's set via the trade modal or `/holdings`, not by dragging holdings between buckets). ADR-0063 brought it back for a narrower purpose: reordering rows in the "축 관리"(`AxisCategoryManagerDialog`) modal, and reordering role buckets on `/portfolio` itself (`RoleAllocationView`). **The two surfaces persist differently, don't assume they share a code path**: the modal saves immediately on drop (`handleReorderCategories`, `pages/portfolio.tsx`, no edit-mode concept there); the `/portfolio` role buckets only allow dragging while `isEditing` and stage the new order in `draftRoleOrder`, persisted by `finishEditingRole` alongside target% changes, discarded on cancel — matching how the old asset-group drag-and-drop worked (edit-mode-gated, part of the draft), not the modal's always-on pattern. Don't reintroduce it for holding-to-bucket assignment on `/portfolio` without checking with the user first — that specific use case is still gone.

## File structure
App code lives under `src/` (`src/pages`, `src/components`, `src/hooks`, `src/lib`, `src/types`, `src/styles`, `src/proxy.ts`) — see ADR-0011. `public/`, config files (`next.config.ts`, `tsconfig.json`, `components.json`, etc.), `docs/`, and `supabase/` stay at the repo root per Next.js convention. Path references below (`lib/...`, `hooks/...`) are relative to `src/`. `infra/` holds non-app infrastructure config (currently `infra/toss-proxy/`, ADR-0053) — not part of the Next.js app, never imported from `src/`.

## Next.js 16 breaking changes
- `middleware.ts` → `proxy.ts`, `export function middleware` → `export function proxy`.

## Code comment language
- Write code comments in Korean (한국어) — identifiers, commands, file paths, and log/error strings stay in English/technical form as usual; only the comment prose is Korean.

## Data model rules
- **`asset_type`/`account` 옵션 목록은 ADR-0061 기준**. 자산종류(`AssetType`, `src/types/domain.ts`)는 개별주식/ETF/ETN/펀드/채권/금현물/현금성(`STOCK`/`ETF`/`ETN`/`FUND`/`BOND`/`GOLD`/`CASH`) 7개 — DB에 `holdings_asset_type_check` CHECK 제약이 걸려있어 값을 빼려면(예: 예전의 `REIT`) 기존 종목을 먼저 다른 값으로 재분류한 뒤 제약을 갱신해야 한다(`supabase/schema.sql` 하단 마이그레이션 블록 참고). 계좌(`account`)는 일반계좌/ISA/연금저축/DC/IRP/기타 6개(`HoldingFormDialog.tsx`/`ExecutionFormDialog.tsx`의 `ACCOUNT_TYPES`) — 이쪽은 CHECK 제약 없는 자유 텍스트라 옵션을 빼도 DB 마이그레이션은 필수가 아니지만, 빠지는 값으로 저장된 기존 종목은 드롭다운에서 선택 불가능한 고아 값이 되므로 남은 옵션으로 재분류할지 확인해야 한다.
- Never persist `current_price` / any live-market-derived value in the DB — always fetched live from Toss at read time and computed in `lib/calc/rebalance.ts`. See the comment in `supabase/schema.sql`.
- A holding with `ticker: null` (e.g. cash-like assets) means "skip live price lookup, use `avgPrice` as the value" in `lib/calc/rebalance.ts`. `HoldingFormDialog` has a KRW/$ checkbox row (below 보유수량/평균매입가) for this: checking one sets `region` to match (국내/해외), disables the 코드/티커 input, and collapses 보유수량+평균매입가 into a single 금액 field — on submit `ticker` is forced to `null`, `qty` to `1`, and the entered 금액 becomes `avgPrice` (see ADR-0022 for the exact DB mapping — there's no dedicated amount column). Unchecked (default) requires a non-empty 티커/코드 + separate 보유수량/평균매입가 as before.
- **Rebalance judgement is role/market-axis-level only, holdings never carry their own target** (ADR-0024, generalized by ADR-0062). `AxisBucketCalc` carries `diff`/`actionAmount`; `HoldingCalc` deliberately has no target/diff/actionAmount at the top level — judging a holding against an unset target produced bogus "매도 필요" signals. Sector rows *do* get a target inside their parent role bucket (see below) but that's the one exception, and it's a loose/non-blocking one.
- **Holdings have no per-holding color** (ADR-0040, reversing ADR-0025) — only axis buckets (role/sector/market) derive a color (`hueForGroupIndex`/`colorFor`, position-based, not stored). Don't reintroduce a `tintForIndex`-style holding tint without checking with the user first.
- **역할·섹터는 `axis_categories` 테이블 하나로 통합**(id/user_id/axis/name/description/target_pct/sort_order, ADR-0063) — 이름·설명·목표%·순서가 같은 모양이라 `axis: "role"|"sector"` 구분 컬럼 하나만 다르다. `holdings.role_id`/`sector_id`가 각각 FK로 참조한다(종목 하나가 역할 하나·섹터 하나만 가지므로 N:M 매핑 테이블이 아니라 `asset_type`과 같은 단순 컬럼 패턴). **역할도 섹터처럼 사용자가 계속 추가·삭제하는 동적 목록**이다 — 더 이상 고정 enum이 아니다(`Role`/`ROLE_LABELS`/`ROLE_ORDER`는 삭제됨, ADR-0063이 ADR-0062의 "고정 5개" 결정을 대체). 기본 역할은 성장/방어/인컴/안전 4개로 시드된다. `holdings.leverage`(기본 1, numeric)는 별개 컬럼으로 남아있고 **비중·한도 계산엔 전혀 안 쓰는 순수 표시용 메타데이터**다(문서가 제안한 "레버리지 명목노출" 개념은 검토 후 기각). `role_id`/`sector_id` 둘 다 nullable이라 null/미분류 상태가 정상 — 강제 배치 화면 없이 매매 모달이나 `/holdings` 편집에서 채운다. `description`(선택, 최대 50자)은 각 카테고리가 뭘 뜻하는지 적어두는 메모 — `/portfolio`의 역할/섹터 행에 이름 아래 작은 글씨로 표시된다.
- **역할·섹터 자체의 CRUD(추가·이름변경·설명·삭제·순서변경)는 `AxisCategoryManagerDialog`(`components/portfolio/`)라는 별도 모달 하나가 담당한다** — 역할용/섹터용 모달을 따로 안 만들고, 모달 내부 세그먼트 버튼(ADR-0051 패턴)으로 축을 전환한다(ADR-0063, `/portfolio` 헤더엔 "축 관리" 버튼 하나만 있음). `/portfolio`의 목표% 편집 모드 안에 CRUD를 끼워 넣지 않는다. 이유: 멤버가 없고 목표%도 0인 카테고리는 역할 버킷을 펼쳐도 안 보이도록 필터링돼 있어서, 비중 뷰 안에 CRUD를 두면 그런 항목을 관리할 방법이 아예 없어지는 문제가 실제로 있었다. 이 모달은 이름·설명·순서만 다루고 목표%는 안 다룬다 — 목표%는 여전히 `/portfolio` 역할 탭 편집 모드(ADR-0036과 같은 "정의/관리" vs "비중 보기" 분리 원칙)에서. 순서 변경은 dnd-kit 드래그로, 드롭 즉시 저장된다(완료 버튼 없음, 옛 `AxisTabs` 탭 순서 변경과 같은 패턴). 삭제 확인은 이 앱의 기존 패턴대로 모달 위에 `AlertDialog`를 얹어 처리한다(오프닝밸런스 목록 다이얼로그와 같은 스태킹 패턴, 아래 매매일지 절 참고). 모달은 `flex flex-col` + **고정 높이**(`h-175` = 700px, `max-h-[85vh]`로 짧은 화면만 축소)로 제목/축 전환/설명/추가 버튼을 고정하고, 목록 부분만 `min-h-0 flex-1 overflow-y-auto`로 스크롤한다 — 목록이 길어져도 헤더나 "+ 추가" 버튼이 화면 밖으로 밀려나지 않는다. **높이가 `max-h`만이 아니라 고정값인 이유**: 역할(보통 몇 개 안 됨)과 섹터(계속 늘어남) 목록 길이가 서로 다른데, 콘텐츠에 맞춰 늘었다 줄었다 하면 "역할"↔"섹터" 탭을 오갈 때마다 모달 크기가 눈에 띄게 바뀌어 산만했다(실제 요청으로 발견) — 고정 높이 + 내부 스크롤로 탭 전환 시에도 모달 크기 자체는 항상 동일하게 유지한다.
- **섹터는 역할에 종속적으로만 나타난다** — 화면상 항상 어떤 역할 버킷 "안에서"만 보이고, 섹터 하나가 여러 역할에 동시에 걸치는 경우는 드물다고 보고 신경 쓰지 않는다(강제하는 제약도 없음). `sectors.target_pct`는 "그 섹터가 속한 역할 버킷 내에서의 목표%"로 해석하고, 역할과 달리 **100% 합계를 강제하지 않는다**(느슨한 참고용 — 미지정 종목이 남는 것도 이 앱의 기존 원칙, 다음 항목과 같은 정신).
- **`holdings.sector_id`가 null이면 "섹터 미지정"** — 강제 배치 없이 정상 상태다(ADR-0059의 "미분류 group_id=null" 정신을 그대로 계승). `RoleAllocationView`가 역할 버킷을 펼칠 때 섹터별로 다시 `computeAxisRebalance`를 중첩 호출하는데, 이때 sector_id가 null인 멤버는 "섹터 미지정" 센티널 버킷(`UNASSIGNED_SECTOR_KEY`, 화면 전용 상수, DB에는 없음)으로 모인다.
- **`ClassificationFieldsBlock`**(`components/shared/ClassificationFields.tsx`)가 역할 칩(`RoleChips`) + 섹터 콤보박스(`SectorCombobox`, Korean-IME-safe) + 레버리지 입력을 한 세트로 묶는다 — 매매 모달(`ExecutionFormDialog`의 "+ 새 종목"과 기존 종목의 "변경" 링크)과 `/holdings`(`HoldingFormDialog`) 양쪽이 이 컴포넌트 하나를 공유한다. 섹터 콤보박스에서 없는 이름을 입력하면 "+ '이름' 새 섹터 만들기"가 나타나고, 고르면 목표% 0으로 즉시 생성해서 바로 지정한다.

## 역할/섹터/시장 축 — ADR-0058, ADR-0062, ADR-0063
- **비중 체크는 2개 고정 탭**(역할/시장)이고 `/portfolio`에서 `?axis=role|market` URL 쿼리 + plain 세그먼트 버튼(`components/portfolio/AxisTabs.tsx`, ADR-0051 패턴 — Tabs 프리미티브 아님)으로 전환한다. **더 이상 유저가 탭을 만들거나 순서를 바꾸지 않는다** — "무제한 커스텀 탭" 시스템(`custom_tabs` 테이블, `TabEditor`/`TabBucketCard`/`UnassignedHoldingsCard` 컴포넌트)을 한 차례 시도했다가 ADR-0062에서 걷어냈다. 편집 모드(수정/취소/완료)와 draft는 페이지 전역 하나 — 역할 탭 안에서 역할 목표%(동적 개수, 반드시 합 100%) + 펼쳐진 섹터들의 목표%를 한 세션에 같이 고친다(`pages/portfolio.tsx`의 `draftRoleTargets`/`draftSectorTargets` useState, key는 둘 다 `AxisCategory.id` — 별도 draft 라이브러리 없이 옛 시장 축 편집(`draftMarketTargets`)과 같은 패턴을 그대로 복제). 이 편집 모드는 목표% 값만 다루고, 역할·섹터 목록 자체의 추가/삭제는 "축 관리" 버튼으로 여는 `AxisCategoryManagerDialog`가 따로 담당한다(ADR-0063, 위 Data model rules 참고). **역할 버킷의 순서변경도 `/portfolio` 화면에서 직접 할 수 있지만, 옛 자산군 드래그와 같은 원칙으로 목표% 편집 모드(`isEditing`) 중에만 가능하고 draft에 포함된다** — `RoleBucketCard`는 `useSortable`을 항상 호출하되 드래그 핸들(따라서 `attributes`/`listeners`)은 `isEditing`일 때만 렌더해서, 편집 모드가 아니면 드래그를 시작할 방법 자체가 없다. 순서는 `draftRoleOrder`(역할 id 배열, `pages/portfolio.tsx`)에 담기고 `finishEditingRole`이 목표%와 함께 바뀐 `sortOrder`만 저장한다 — 취소하면 순서도 버려진다. **"축 관리" 모달 안의 순서변경은 이 규칙과 다르다** — 그 모달은 편집 모드 개념이 없는 별도 관리 화면이라 여전히 항상 가능하고 드롭 즉시 저장된다(옛 `AxisTabs` 탭 순서 변경과 같은 원칙, `handleReorderCategories` 재사용). 시장 축은 버킷이 고정 3개라 애초에 드래그 대상이 아니다.
- **변동성 축(공격/중립/방어)은 만들었다가 뺐다** — σ 절대 임계값 방식이 주식 위주 포트폴리오에 안 맞아서(SCHD가 중립 등) **분류 기준이 아직 안 정해짐**. 관련 코드(`useRiskMetrics`, `lib/calc/risk.ts`, `RiskSummary`, `tossHistoryProvider`, `price_daily`, `/api/toss/history`) 전부 삭제. 재도입은 ADR-0058 ③ + 이 프로젝트의 열린 질문 참고 — git 기록에서 되살릴 수 있다. 시장 베타·주식 상관 기반 역할 적정성 경고("측정값", 별도 명세 문서가 제안)도 정확히 같은 이유(파이프라인은 있지만 판단 기준 미확정)로 ADR-0062에서 제외했다.
- **축 ① 시장** (구현됨, 변경 없음): `holdings.exposure_region` (`Holding.exposureRegion: "한국" | "미국" | null`, ADR-0058). `region`(상장 시장·통화)과 **다른 개념** — 실질 익스포저 지역이다. `null` = "특정 국가 익스포저 아님"(현금·채권·원자재) → 시장 축에서 "기타" 버킷. 종목 폼 2곳(`HoldingFormDialog`, `ExecutionFormDialog`의 "+ 새 종목")에 "실질 지역" Select 있음 — 기본값은 `deriveExposureRegion(region)`(`lib/calc/axisRebalance.ts`, 국내→한국/해외→미국), 사용자가 KRX 상장 미국 ETF·현금성일 때 바꾼다. `한국/미국` 2개만인 건 의도적(글로벌 버킷·per-holding us_weight 기각) — 일본/중국/인도 등 실제 투자 시 확장.
- **축 ② 역할**: 고정 5개(성장/방어/인컴/헤지/현금성). `bucketOf = h.role`, 목표는 `axis_targets`에 `axis: 'role'`로 저장(시장 축과 같은 테이블·API 재사용). 반드시 합 100%(다른 축과 달리 강제).
- **역할 안의 섹터 중첩** (`RoleAllocationView`, `components/portfolio/RoleAllocationView.tsx`): 역할 버킷 하나를 펼치면 `computeAxisRebalance`를 그 버킷의 멤버(`bucket.members`)만 대상으로 **다시 한 번** 호출해 섹터별로 쪼갠다 — 계산 엔진 자체는 안 건드리고 중첩 호출로 해결한 것. 성장뿐 아니라 방어·인컴·헤지·현금성 전부 동일하게 섹터로 쪼개진다(섹터가 어느 역할에 나타날지 미리 알 수 없으므로). 목표% 합계 100% 강제 없음(위 Data model rules 참고).
- **`computeAxisRebalance`** (`lib/calc/axisRebalance.ts`) — 버킷/목표% 계산 엔진. `bucketOf`(null이면 축에서 제외)와 `targets` Record만 바꿔 어떤 축(역할/섹터/시장)이든 같은 계산식으로 굴린다. `diff`/`actionAmount` 부호·색 규칙은 `diffColor`(`lib/calc/rebalance.ts`) 재사용. 시장 축은 `AxisAllocationView`(도넛 2개 + 버킷 행 + 펼침 종목 목록, 편집 모드 지원), 역할 축은 `RoleAllocationView`(같은 도넛 UI + 섹터 중첩)가 렌더 — 둘은 별개 컴포넌트다(섹터 중첩 구조가 있어 `AxisAllocationView`를 그대로 못 씀).
- **`axis_targets` 테이블** (`user_id, axis, bucket` PK, `axis in ('market', 'role')`) — 시장·역할 축의 버킷별 목표%. 섹터는 안 쓴다(`sectors.target_pct`에 직접 저장, 역할에 종속적이라 별도 버킷 키 체계가 필요 없음). `lib/api/axisTargets.ts`의 `saveAxisTargets`는 "완료" 시점에 그 축 행을 통째로 delete 후 0보다 큰 것만 insert(autosave 아님, ADR-0007). 시장·역할 축 둘 다 합계 100% 강제(전부 0이어도 예외 없음 — 시장 축은 "설정 안 함"을 허용하지 않는다).
- **`/holdings`의 필터는 축별 독립 필터**(지역/실질지역/역할/섹터/계좌, `HoldingsFilterBar.tsx`) — 서로 종속관계 없다. 옛 "포트폴리오(탭)+버킷" 2단 종속 셀렉트(ADR-0062 이전 커스텀 탭 시절)를 대체한다. 이 화면의 필터는 비중 조절이 아니라 종목 조회·수익률 확인이 목적이라는 점이 이 교체의 근거다.

## Trading journal (매매일지) — ADR-0027~0032, 0038, 0041~0054
- **`executions` is the only write path for `holdings.qty` / `holdings.avg_price`** (ADR-0027, ADR-0044). Those two columns are a materialized replay of the ledger. Never `update` them directly — go through `lib/journal/commit.ts`, which replays and persists. `HoldingFormDialog` (`/holdings`) doesn't even collect qty/avgPrice anymore — new holdings are created at qty 0 and filled by the first execution. `computeRebalance` and every read path keep consuming `holdings` unchanged.
- A holding's pre-journal balance is one `intent = 'OPENING_BALANCE'` execution, entered via the "기초잔고" checkbox that only appears inside `ExecutionFormDialog`'s "+ 새 종목" flow (ADR-0050) — it does *not* appear when picking an existing holding, buying or selling, since at most one opening balance is allowed per holding (DB-enforced via a unique partial index) and an existing holding by definition already has its trade history started. There's currently no UI path to backfill an opening balance onto a holding that was created via `/holdings` metadata-only and later needs it (known gap, see ADR-0050 Consequences) — a same-day regular BUY is the workaround. **Opening balance has no `executed_at`** (`executions.executed_at` is nullable, `NEW` intent still requires it — ADR-0048) — it's not a "매매일" concept, so don't resurrect a date input for it. `/journal`'s calendar/day-list excludes OPENING_BALANCE rows entirely (they'd have no date to place them on); they're only visible via the "기초잔고 보기" button/list on that page, which also hides `ExecutionsTable`'s 날짜/실현손익 columns (`showDateColumn`/`showRealizedPnlColumn` props) since those are always empty for opening-balance rows. That dialog keeps `max-h-[85vh] overflow-y-auto` (dropping it let content overflow the viewport when the list got long — a real bug, not just style) plus `scrollbar-hidden` so the scroll still works but the bar doesn't show. `ExecutionsTable` no longer has a per-row "기초잔고" badge at all — it was only ever needed for calendar rows, and ADR-0048 already excludes OPENING_BALANCE from the calendar, so the badge component became fully dead (`OpeningBalanceBadge.tsx` was deleted; `OpeningBalanceHelp.tsx` — a "?" popover trigger with the same explanation, used once in the "기초잔고 보기" dialog title — is what's left). `replayHolding`'s sort treats OPENING_BALANCE as always-first regardless of date (there's at most one per holding, so no ambiguity) rather than comparing dates. Clicking "수정" or the delete icon on a row inside the "기초잔고 보기" list opens `ExecutionFormDialog`/`AlertDialog` **without** closing the list dialog behind it — dialogs stacked simultaneously, deliberately, so finishing the edit or confirming the delete drops the user back into the list instead of forcing them to reopen it. This relies on base-nova's `Dialog`/`AlertDialog` being portal-based with independent per-instance `open` state (each instance handles its own focus trap/Escape/backdrop dismissal) rather than any bespoke stacking logic — don't add one. The list refreshes itself after a delete same as any other prop update: `deleteExecution`'s `onSuccess` invalidates the `executions` query, `openingBalanceExecutions` (a `useMemo` over that query's data) recomputes, and `ExecutionsTable` re-renders with the deleted row gone — portal rendering only changes *where in the DOM* the dialog's children mount, it doesn't opt them out of normal React re-rendering.
- **New holdings are always a BUY** (ADR-0050) — you can't sell something you don't have yet. `ExecutionFormDialog` locks the side to BUY and hides the toggle (shows a fixed label instead, same as edit mode) whenever "+ 새 종목" is active. The "+ 새 종목" field set is grouped into two-column rows inside the dashed box — 자산종류/지역, 계좌/코드(티커), 종목명 — followed by the 역할·섹터·레버리지 분류 블록(`ClassificationFieldsBlock`, ADR-0062, see Data model rules), the 기초잔고 checkbox, then qty/price (or a single 금액 field), then the KRW/$ cash-like checkbox row. That new-holding flow now collects `assetType` directly (reusing `ASSET_TYPE_LABELS`/`AssetType` from `@/types/domain`, no help-popover here unlike `HoldingFormDialog`) — ADR-0047's "journal doesn't ask, defaults to ETF" call was reversed by ADR-0050.
- Recording a buy for a ticker that has no holding creates the holding with **qty 0** and lets the execution fill it. Don't write an OPENING_BALANCE for that case.
- `replayHolding` (`lib/journal/replay.ts`) is a pure function and must stay one — partial recalculation was deliberately NOT implemented (ADR-0032), because a second implementation would need its own proof that it matches. Oversold executions abort the whole replay (`OversoldError`); no partial state is persisted.
- **`commitExecutionDelete` (`lib/journal/commit.ts`) dry-runs the replay *before* touching the DB** — it replays the holding's remaining executions (the one being deleted excluded, purely in memory) and throws `OversoldError` if that would leave a SELL oversold, only calling `softDeleteExecution`/`replayAndPersistHolding` once that check passes. Found as a real bug: it used to `softDeleteExecution` first and replay after, but unlike `commitNewExecution` it had no revert-on-failure — so an oversold-producing delete (e.g. deleting a holding's sole OPENING_BALANCE while a later SELL only balances against that opening quantity) left the execution permanently soft-deleted in the DB while the user saw a plain "삭제에 실패했습니다" toast and `holdings.qty/avg_price` went stale, silently out of sync with the ledger. Deleting an OPENING_BALANCE (or any execution) that leaves the remaining ledger internally consistent is NOT blocked, even with later BUYs on top of it — that's a legitimate correction (e.g. "this was mis-entered as an opening balance, it should've been a dated BUY"), so there's no blanket rule against deleting an early execution just because later ones exist; only an actual oversold outcome is refused. `journal.tsx`'s `handleDelete` catches `OversoldError` with its own message ("...삭제하지 않았습니다"), matching the pattern `handleSubmit`/`handleUpdate` already use.
- **Every execution read needs `deleted_at IS NULL`** (soft delete, ADR-0032). `lib/api/executions.ts` applies it by default — keep it that way and expose deleted-inclusive reads as separate functions.
- **Fees/taxes are not modeled at all** (ADR-0034, reversing ADR-0028) — broker/event discount rates vary too much for a fixed rate table to be worth the upkeep. `executions` has no fee/tax columns. `computeExecutionAmount` (`lib/journal/cost.ts`) only computes `grossAmount`/`netCashFlow` from qty×price. Don't reintroduce a rate table without checking with the user first.
- **`executions` has no FX column at all** (ADR-0038, reversing ADR-0029) — realized P&L (`ClosedLot.realizedPnl`) is always in the holding's native currency (USD for 해외, KRW for 국내), never converted. Live FX (`useExchangeRate`) is for **평가금액 only** — don't reintroduce an fx input on the execution form or a KRW-converted realized-P&L field without checking with the user first. `pages/journal.tsx`'s `closedLotByExecutionId` replays every holding's full execution history (pure, cheap) to show realized P&L inline per SELL row — the first place this app surfaces it.
- All money math goes through `roundCurrency` / `normalizeQty` (`lib/journal/cost.ts`). The project stays on `number` instead of Decimal (ADR-0030), so those two functions are the *entire* defence against float error — a plain `qty * price` multiplication can land on something like `X.99999999999999` in IEEE754, which floors to one unit low without the rounding guard. Verified failure, not hypothetical.
- `trade_notes.body` is free text and must never feed an aggregate (ADR-0031/0041/0042 — structured setup/emotion tags were tried and removed). One note per execution via `execution_id` FK, not per holding/position (ADR-0043 — POSITION/DAY-targeted notes were removed).
- Editing an execution's note to empty must actually **delete** the `trade_notes` row (`deleteTradeNote`/`useDeleteTradeNote`, `lib/api/tradeNotes.ts`), not silently skip the save. `ExecutionFormDialog`'s edit-mode `handleSubmit` passes `note: ExecutionNoteDraft | null` (never `undefined`) to `onUpdate` — `null` means "clear it," and `journal.tsx`'s `handleUpdate` branches on that to call delete instead of upsert. This is edit-only: the add-flow's `buildNoteDraft()` still returns `undefined` for an empty body so a brand-new execution doesn't create an empty note row (there's nothing to delete yet). Found as a real bug — clearing an existing note and saving silently left the old body in place, because `handleUpdate`'s `if (note)` guard treated an empty draft as "nothing to do" instead of "clear it."
- `/journal` has two view modes — 기간 (calendar + presets + custom range, merged from the former separate 달력/기간 modes, ADR-0052) and 종목 (one holding's entire history, opening balance included, no date bound) — switched via plain toggle buttons, not a new UI primitive (ADR-0051). Both read from the same already-fully-fetched `executionsQuery.data`/`tradeNotesQuery.data` — no new Supabase queries, no pagination; `executions`' existing `(holding_id, executed_at)`/`(user_id, executed_at)` indexes already cover both access patterns. 기간/종목 modes intentionally have their own parallel `summarizeExecutions`/`useHistoricalFxRates`/`rateForExecution` trio (`periodSummary`/`periodFxQuery`/`periodRateForExecution` vs `holdingSummary`/`holdingFxQuery`/`holdingRateForExecution`) rather than sharing one — don't merge them without a reason. 종목 mode's 매수/매도 근거 are two separate columns (`NotesColumn` × 2), not one interleaved timeline — reuses `notesForSide` (a both-sides generalization of `ExecutionFormDialog`'s BUY-only `buyNotesFor`), not the same function. 종목 mode's `TradeSummaryStrip` includes the opening balance in its 매수/매도 totals (unlike 기간, which excludes it entirely since it has no date) — since it has no `executedAt`, its portion is converted with `useExchangeRate`'s **today's live rate** instead of `useHistoricalFxRates`; `holdingRateForExecution` branches on `executedAt` presence to pick the right source. This means 종목 mode is the one view that keeps `useExchangeRate` polling (1-minute interval) while open, on top of the historical-rate query 기간 mode already uses.
- 기간 mode's date filtering has two **mutually exclusive** sources gated by `selectionMode: 'range' | 'days'` (ADR-0052) — presets and the custom `type="date"` inputs (`applyRange`) set `selectionMode: 'range'` and filter by a plain `[periodRange.start, periodRange.end]` comparison; clicking individual calendar cells (`toggleDay`) sets `selectionMode: 'days'` and filters by membership in `selectedDays` (a `Set<string>`, toggled one date at a time, including empty dates). **Clicking a preset never marks any calendar cell as "selected"** — this is deliberate, not an oversight: an earlier version filled `selectedDays` from every preset click, which meant narrowing a preset-selected month down to one day required deselecting every other day by hand. Now a single calendar click unconditionally drops you out of range mode into days mode showing just that day, and going back to a preset is one pill click away — no "clear selection" button needed. `shiftMonth` never touches selection state (days must survive month navigation, since picking days across multiple months is the point). `goToToday` is the one exception — unlike `shiftMonth`, it *does* replace the selection with today (`setSelectionMode('days')` + `setSelectedDays(new Set([today]))`, not a toggle-add) — a dedicated "오늘" button implies "show me today," not just "scroll the calendar there," so leaving the old selection in place would be surprising. The right-panel label (`periodLabel`) differs by mode too: range mode shows `start ~ end` (or just one date if they're equal); days mode runs `selectedDays` through `formatSelectedDays`, which groups only **contiguous** dates with `~` (e.g. picking the 17th and 19th renders `2026-08-17, 2026-08-19`, not `2026-08-17 ~ 2026-08-19` — the latter would wrongly imply the 18th is included too).
- `ExecutionsTable`'s rows have inline edit/delete icon buttons (same `Pencil`/`Trash2` pattern as `HoldingsTableRow`), not a row-click detail modal — a detail modal was tried (`ExecutionDetailDialog`) and removed for being redundant with the row itself (ADR-0049). Delete goes through an `AlertDialog` confirm first. Editing an execution can't change its 매수/매도 side (rendered as a fixed label instead of the add-mode toggle) or its holding — same reasoning as not supporting holding reassignment (ADR-0039).
- **Selling a holding down to `qty === 0` auto soft-deletes it** (ADR-0054) — `lib/journal/commit.ts`'s `replayAndPersistHolding` (the one choke point every execution write goes through, ADR-0027) calls `deleteHolding` right after persisting a `qty === 0` replay result, unless it's already deleted. No auto-restore in the other direction — re-buying a fully-exited ticker is always "+ 새 종목" from scratch (no group/account/target prefill), deliberately, since the re-entry might belong in a different asset group this time. **Two holdings queries now exist**: `fetchHoldings`/`useHoldings` (active only — `/holdings`, `/portfolio`, and `ExecutionFormDialog`'s "보유종목에서 고르기" picker, since that one has to offer only what you can actually attach a trade to) vs `fetchAllHoldings`/`useAllHoldings` (includes soft-deleted — `journal.tsx` uses this exclusively for `holdingById` and everything downstream of it). Before this ADR, `journal.tsx`'s `holdingById` was active-only too, which meant a fully-exited holding's past executions rendered as `'삭제된 종목'` (`ExecutionsTable.tsx`'s fallback) in 기간 mode instead of their real name — a real bug this incidentally fixed, not just a 종목 mode enhancement. 종목 mode groups holdings by **ticker+region only** (`holdingIdentityKey`, ignores account) so a ticker's full history survives across a delete-then-rebuy cycle — selecting one combobox entry resolves to every `holding_id` sharing that identity and unions their executions. Don't add a "기존 종목에서 고르기" label back on the execution-form picker — it's "보유종목에서 고르기" now specifically to distinguish it from 종목 mode's all-time search.

## Portfolio page edit pattern (draft/staging, not autosave)
`/portfolio`'s edit mode is plain component `useState` draft, not a shared draft library — entering edit mode seeds `draftMarketTargets`/`draftRoleTargets`/`draftSectorTargets` from server state, and **nothing** touches Supabase until "완료" is clicked (`finishEditingMarket`/`finishEditingRole` in `pages/portfolio.tsx`). "취소" discards the draft with zero server calls. Don't reintroduce onBlur-autosave on this page.
- **Holding CRUD lives on `/holdings` only** (ADR-0036) — `/portfolio`'s edit mode only edits target percentages (role/sector/market), never individual holdings. Reclassifying a holding's role/sector happens via the trade modal or `/holdings`, not by dragging it anywhere on `/portfolio` — **there is no drag-and-drop on this page anymore** (dnd-kit removed, ADR-0062, see Stack). `EditHoldingInlineRow`/`EditGroupCard`/`GroupCard`/`GroupHoldingsPanel`/`TabEditor`/`TabBucketCard`/`UnassignedHoldingsCard` are all gone — don't resurrect drag-based bucket assignment on this page without checking with the user first.

## Toss API quirks
- Every response is wrapped in a `{"result": ...}` envelope — undocumented, only discovered via direct `curl` against the real API. Zod schemas must unwrap `.result`.
- No WebSocket support ("추후 지원 예정"). Poll at 1-minute intervals (`hooks/useLivePrices.ts`, `hooks/useExchangeRate.ts`) with adaptive backoff on rate-limit signals — never assume sub-minute polling is safe.
- Fields like `timestamp`/`currency` can come back `null` (not just absent) for non-priceable symbols — Zod schemas need `.nullish()`, not `.optional()`.
- `/api/v1/exchange-rate`는 **라이브 시세 전용, 과거 날짜 조회 파라미터 자체가 없다** — `date` 같은 파라미터를 붙여봐도 무시되고 항상 현재 시세가 온다(2026-08-25 직접 curl로 확인). 응답의 `validFrom`/`validUntil`(문서에 없는 필드)을 보면 그 차이가 약 5분이라, Toss 내부적으로 환율이 대략 5분 간격으로 갱신된다는 뜻 — `useExchangeRate`의 1분 폴링(ADR-0005)이 왜 충분한지 설명이 된다. `/api/v1/candles`에 `USDKRW` 같은 통화쌍 심볼을 넣으면 `stock-not-found`로 거부됨 — 그 엔드포인트는 주식 전용이라 통화쌍 히스토리컬 조회 용도로 쓸 수 없다(과거 체결일 환율은 `lib/fx/frankfurterProvider.ts`의 별도 소스로 대체하는 이유). **현재값(Toss)과 과거 확정값(Frankfurter) 두 경로를 언제 어디서 쓰는지는 ADR-0055에 통합 정리돼 있다** — 새 화면에 환율이 필요하면 이 ADR부터 확인해서 맞는 훅을 고를 것, 섞어 쓰면 조용히 틀린다. 과거 환율은 `fx_rate_daily` 테이블(유저 스코핑 없음, `rate_date` PK, ADR-0055)에 read-through로 캐시된다 — `getUsdKrwHistoricalRates`(`lib/fx/frankfurterProvider.ts`)가 `SupabaseClient`를 받아 캐시를 먼저 읽고, 빈 날짜가 있을 때만 Frankfurter를 부른 뒤 그 결과를 `lib/api/fxRateCache.ts`의 `upsertFxRates`로 저장한다 — Toss의 라이브 환율(평가금액용)은 이 캐시와 무관하니 섞지 말 것.
- Toss requires calls to come from a whitelisted fixed IP, which a Vercel-deployed serverless function can't guarantee — production routes all Toss calls through an Oracle Cloud reverse proxy VM (ADR-0053, runbook in `infra/toss-proxy/README.md`). Every outbound Toss call (`tossAuth.ts`'s OAuth token fetch, `tossPriceProvider.ts`, `tossFxProvider.ts`, `tossCandleProvider.ts`) goes through the `tossFetch` helper (`lib/toss/tossAuth.ts`), which reads `TOSS_PROXY_BASE_URL`/`TOSS_PROXY_SHARED_SECRET` env vars — never call Toss with a raw `fetch` from a new call site, or it'll bypass the proxy in production. Both env vars are optional and unset locally, so local dev keeps calling Toss directly, unchanged.
- **Toss invalidates the previous OAuth access token the instant a new one is issued for the same `client_id`** — verified directly (2026-08-25): token A works, requesting token B immediately makes token A return `401 invalid-token`. Vercel serverless containers each hold their own independent in-memory `cachedToken` (see the comment in `tossAuth.ts`), so one container minting a fresh token silently kills whatever token another container still thinks is valid — this surfaced as frequent `502`s from `/api/toss/exchange-rate` and friends. All three data-fetching providers call Toss exclusively through `tossAuthedFetch` (`lib/toss/tossAuth.ts`), which retries once with a freshly-minted token on any `401` — never call `tossFetch` with a manually-attached `Authorization: Bearer` header from a new call site, or that call site loses the auto-recovery. A DB-backed shared/locked token cache would eliminate the race entirely but was judged overkill for this app's traffic; revisit if 401s start recurring even after the retry.
- The VM's `infra/toss-proxy/nginx.conf` must reference `openapi.tossinvest.com` through a `resolver` + `set $var` pair, never as a literal `proxy_pass https://openapi.tossinvest.com;` — a literal domain gets DNS-resolved once at nginx startup/reload (`nginx -t` time) and cached forever. This actually took the proxy down for hours (2026-08-24): Ubuntu's daily unattended-upgrades restarted `systemd-resolved`, nginx's own restart landed in that same DNS-down window, `nginx -t` failed with "host not found in upstream", and nginx refused to start with no auto-retry — Vercel saw `ECONNREFUSED` on every Toss call until someone noticed and manually restarted it. Fixed by resolving via variable (request-time, respects the `resolver`'s `valid=` TTL) and adding a `Restart=on-failure` systemd override so any future one-off failure self-heals instead of sitting dead.

## UI conventions
- **Never use `<input type="number">`** bound directly to a numeric state with per-keystroke `Number(e.target.value)` — causes a leading-zero bug. Use `type="text"` + `inputMode="decimal"` with local string draft state, parsed on blur. Reuse `useEditableField`/`useEditableNumberField` (`hooks/useEditableField.ts`) rather than reinventing this.
- shadcn `<Select>` needs an explicit `items` prop on the root or the trigger shows the raw value instead of the resolved label.
- Delete unused generated files outright (e.g. shadcn components that end up unused) rather than leaving dead code or stripped-down stubs.
- Title-weight text (page `<h1>`s, group/item names, nav logo) uses `font-semibold`, not `font-bold`.
- "On target" / success states use the app's mint `GOOD_COLOR` (exported from `lib/calc/rebalance.ts`), not a generic green — keep this the one semantic "good" color across pages.
- Signed diffs follow the **Korean market convention: plus = red, minus = blue** (ADR-0026) — the inverse of the US green-up/red-down scheme, so don't "correct" it. `diffColor` (`lib/calc/rebalance.ts`) colors a diff by **sign alone** (a small rise is still a rise). Values live in theme-aware CSS variables (`--diff-rise`, `--diff-fall` in `styles/globals.css`), not hardcoded — one fixed pair can't stay legible on both the near-white and the dark card, and saturated blue in particular falls below a 3:1 contrast ratio on the dark card unless lightened. There used to be a second, threshold-gated `actionColor`/`actionLabel` pair for a "유지/매수 필요/매도 필요" verdict (plus `REBALANCE_THRESHOLD` and `--diff-rise-strong`/`--diff-fall-strong` CSS vars) — removed when the standalone 비중 체크 page folded into `/portfolio` (ADR-0056); the CSS `-strong` vars are still defined in `styles/globals.css` but unused. Don't reintroduce that verdict system without checking with the user first.
- `shortHoldingLabel` (`lib/format.ts`) is the label for tight spots (the group donut's center readout): ticker for 해외 holdings, plain 종목명 for everything else. Don't try to strip brand prefixes from 국내 names — that was tried and rolled back (names like `KODEX 200` degrade to a bare `200`).
- The standalone "비중 체크" page (`/rebalance`) was folded into `/portfolio` (ADR-0056) — there is no separate rebalance-check page/route/nav item anymore. On the 시장 axis, `AxisAllocationView`'s collapsed `BucketCard` row (`components/portfolio/AxisAllocationView.tsx`) shows 목표%/실제%/차이 in fixed-width `w-16` label-over-value columns (차이 uses `diffColor`, sign-only, no verdict badge).   - **역할 확대(줌)**: 그룹 사각형을 클릭하면 `zoomedGroupId`가 그 그룹으로 좁혀지고, `<Treemap data>`에 그 그룹 하나만 담긴 배열을 넘긴다 — depth1(그룹)/depth2(종목) 트리 구조는 그대로 두고 배열 길이만 1로 줄이는 것뿐이라, squarify가 그 그룹을 캔버스 전체에 채워서 "확대"가 저절로 일어난다(별도의 flat 렌더 모드를 만들 필요 없음). 그룹의 depth-1 사각형은 leaf들에 완전히 가려지므로(nodeInset 여백만 노출), leaf `<g>`에도 같은 `onGroupClick`을 걸어야 그룹 영역 아무 데나 클릭해도 확대된다 — 테두리만 클릭 가능한 건 버그였다. 브레드크럼("← 전체")으로 되돌아간다. 이 depth-1 그룹은 `/holdings`의 `heatmapBucketOf`가 역할(role) 기준으로 넘겨준다(ADR-0062) — 예전엔 선택된 포트폴리오 탭 기준이었다.
  - **동적 폰트/말줄임**: 타일 폭에 안 맞으면 `NAME_SIZES`/`PCT_SIZES`(13→9pt)를 순서대로 시도하고, 가장 작은 크기에서도 안 맞으면 이진탐색으로 말줄임(`…`)한다 — 그마저 공간이 없으면 라벨을 아예 생략한다(`estimateTextWidth`는 실측 대신 한글/CJK 1.05em·라틴/숫자 0.62em 근사치를 쓴다). 확대(줌)로 타일이 커지면 같은 로직이 자동으로 더 큰 폰트/전체 이름을 골라준다 — 별도 "확대 모드 전용" 폰트 로직은 없다.

## Lint / build discipline
- React purity ESLint rules (`react-hooks/set-state-in-effect`, `react-hooks/purity`, `react-hooks/immutability`) are enforced strictly: no mutating a local variable across a `.map`/loop during render (use `reduce`/derive per-item instead), no synchronous `setState` in an effect body (only from subscription/interval callbacks), no impure calls (`Date.now()`, `crypto.randomUUID()` outside event handlers, etc.) during render.
- Before considering any change done, run `pnpm typecheck && pnpm lint && pnpm build` — all three must pass clean.

## Security
- Never print secrets (tokens, `.env` values) in tool output. When redacting config/secret-adjacent data, redact recursively — including array elements, not just dict values (a past redaction script missed array-nested strings and leaked a live Supabase PAT).
