# ADR-0039: 매매일지에 체결 수정 진입점을 추가하고, 종목 재배정은 지원하지 않는다

## Status
Accepted

## Context

체결을 고치는 데이터 계층(`commitExecutionUpdate`, `useUpdateExecution`)은 이미 있었지만
`/journal` 어디에도 이걸 호출하는 UI가 없었다 — 체결을 잘못 기록하면 지우고 다시
넣는 수밖에 없었다.

## Decision

- `ExecutionList`(`pages/journal.tsx`)의 각 행에 연필 버튼을 추가해 `ExecutionFormDialog`를
  **수정 모드**로 연다(`editingExecution` prop). 수정 모드에서는:
  - 구분(매수/매도)·수량·단가·체결일시·매매 의도만 고칠 수 있다.
  - **종목은 고정된다** — `<Select>`를 비활성화한다. `commitExecutionUpdate`가
    `holding` 파라미터 하나만 받아 그 종목만 리플레이하기 때문에, 만약 patch로
    `holdingId`를 바꾼다면 원래 종목은 (빠진 체결 반영이) 갱신되지만 새로 옮겨간
    종목은 전혀 리플레이되지 않아 보유수량·평균매입가가 잘못된 채로 남는다. 종목을
    잘못 골랐다면 이 체결을 지우고 올바른 종목으로 새로 기록해야 한다.
  - 근거(태그·청산조건 등) 섹션은 숨긴다 — 근거는 이 다이얼로그를 통한 별도
    편집 경로가 없는 엔티티라, 수정 모드에 섞으면 "체결 수정"과 "근거 수정"이라는
    서로 다른 두 저장 흐름이 뒤섞인다.
  - 매매 의도의 "신규진입" 선택지는 평소엔(새 체결 추가 시) 기존 보유 종목에서
    빠지지만(ADR-0036 이후 추가된 규칙), 이미 신규진입으로 기록된 체결을 수정할
    때는 계속 보여준다 — 그렇지 않으면 그 값을 수정 화면에 열자마자 다른 값으로
    강제 변경되는 것처럼 보인다.
  - 오버셀 여부는 클라이언트에서 미리 막지 않는다 — "지금 보유 수량과 입력값 비교"라는
    기존 휴리스틱이 "기존 체결 하나를 고치는" 상황엔 맞지 않기 때문에, 서버 쪽
    리플레이(`OversoldError`)가 최종 판단을 하게 둔다.

## Consequences
- 잘못 기록한 체결(수량·단가·날짜·구분 오타)을 지우고 다시 넣지 않고 바로 고칠 수 있다.
- 종목을 잘못 고른 경우는 여전히 "삭제 후 재입력"이 유일한 경로다 — 두 종목을 동시에
  올바르게 리플레이하는 기능을 만드는 것보다 이 제약을 문서화하는 쪽을 택했다.
