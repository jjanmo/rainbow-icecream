# ADR-0027: 보유 수량·평균매입가는 체결 원장에서만 계산한다 (기존 보유는 기초잔고 체결로 흡수)

## Status
Accepted — "수동 보유 편집 UI 제거는 하지 않는다"는 절충은 [ADR-0044](./0044-holdings-balance-write-only-via-journal.md)에서 뒤집혔다. 그 절충이 실제로 두 건의 수량 드리프트를 냈다.

## Context

매매일지를 추가하면 같은 사실을 기록하는 경로가 두 개가 된다 — 일지에 매수를 적는 것과 보유 종목에서 수량을 고치는 것. 두 경로를 모두 열어두면 반드시 어긋나고, 어느 쪽이 맞는지 판단할 근거가 없다. 결국 둘 중 편한 쪽만 쓰게 되어 두 기능 모두 신뢰를 잃는다.

원본 설계는 이 문제를 "체결이 단일 진실 공급원이고 보유는 파생값"으로 풀면서 **수동 보유 편집 UI를 제거**하라고 했다. 하지만 이 앱에서 수동 편집은 이미 핵심 UX다(ADR-0006 모달 편집, ADR-0007 드래프트 편집, ADR-0014·0015 인라인 편집). 그리고 이 앱에는 매매일지 도입 전에 쌓인 보유 데이터가 이미 있다.

## Decision

**`executions` 테이블이 보유 수량·평균매입가를 바꾸는 유일한 쓰기 경로다.** `holdings.qty` / `holdings.avg_price` 는 그 원장을 리플레이한 결과를 저장해둔 값(materialized)이며, 언제든 원장에서 다시 만들 수 있어야 한다. 다시 만든 값이 저장값과 다르면 그것은 버그다.

- 리플레이는 순수 함수 `replayHolding`(`lib/journal/replay.ts`) 하나로 구현하고, 쓰기는 `lib/journal/commit.ts` 만 담당한다. 다른 계층은 `qty`/`avg_price` 를 직접 쓰지 않는다.
- **매매일지 도입 전 잔고는 `intent = 'OPENING_BALANCE'` 체결 한 건으로 흡수한다**(`supabase/schema.sql` 하단의 멱등 마이그레이션). 이렇게 하면 "기존에 갖고 있던 것 + 앞으로 기록하는 것"이 하나의 수식으로 합산된다.
- 체결 입력 시 해당 종목이 없으면 **수량 0으로 새 종목을 만들고** 그 체결이 보유를 채운다. 기초잔고가 아니므로 `OPENING_BALANCE` 를 쓰지 않는다.
- 취득원가는 **이동평균법으로 고정**한다. 국내 증권사 화면이 보여주는 값과 일치시키는 게 우선이다. FIFO 선택은 `ClosedTrade.avgEntryPrice` 의 의미가 방식에 따라 달라지는 문제를 안고 오므로 v1 비범위.
- 보유 수량이 음수가 되는 체결은 **아무것도 반영하지 않고 거부**한다.

## Consequences

- 포트폴리오와 일지가 구조적으로 어긋날 수 없다. 과거 체결을 뒤늦게 입력해도 현재 상태가 자동으로 맞춰진다.
- "왜 평단이 이 값인가"를 체결 목록으로 설명할 수 있다.
- 기존 수동 편집 UI는 남는다. 다만 `qty`/`avg_price` 를 직접 고치는 경로는 원장과 어긋날 수 있으므로, 이후 마일스톤에서 **기초잔고 체결을 편집하는 형태로 바꿀 것**을 전제로 남겨둔다. 그때까지는 체결이 있는 종목의 수동 편집이 다음 리플레이에서 덮어써진다는 한계가 있다.
- Supabase 는 클라이언트에서 닿는 크로스 테이블 트랜잭션이 없다. 체결 저장 후 리플레이가 실패하면 방금 넣은 체결을 soft delete 로 되돌린다 — 오염된 상태를 다음 리플레이가 물려받지 않게 하는 쪽이 중요하다.

## 대안

- **양방향 동기화**: 충돌 해석 규칙이 필요하고 그 규칙이 항상 틀린다. 기각.
- **일지를 기록 전용 메모로만 사용**: 이중 기록 문제를 그대로 남긴다. 기각.
