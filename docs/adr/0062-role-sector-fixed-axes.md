# ADR-0062: 자유 커스텀 탭을 걷어내고 "역할(고정)→섹터(자유, 종속)" 2단 분류로 교체

## Status

Accepted — **"역할은 고정 5개 enum"이라는 부분만 [ADR-0063](./0063-unify-role-sector-axis-categories.md)으로
대체됨** (역할도 섹터처럼 동적 목록이 되고, 기본값이 4개로 바뀜). 이 문서의 나머지
결정(역할·섹터 2단 종속 구조, 매매 시점 입력, FK 컬럼 아키텍처, 커스텀 탭 폐기)은
그대로 유효하다.

## Context

`/portfolio`를 "탭을 몇 개든 자유롭게 만들고, 탭마다 버킷을 만들고, 종목을 드래그로
배정하는" 방식으로 일반화하는 작업이 진행 중이었다(커밋되지 않은 상태로 코드에 이미
반영, `custom_tabs`/`custom_tab_buckets`/`custom_tab_holding_buckets` 테이블도
프로덕션 Supabase에 마이그레이션 적용됨 — 사용자가 실제로 "자산군"·"역할기반" 두 탭을
만들어 51/67종목을 배정해 쓰고 있었다).

이후 공유된 별도 명세 문서("포트폴리오 분류 축 설계와 앱 적용 명세", 2026-09-25)는 이
탭 방식을 폐기하고 축 기반 분류로 바꾸자고 제안했다 — 탭마다 종목을 배정하면 미배정
종목이 생기고 탭끼리 분모가 달라져 총자산 기준 판단이 어렵다는 문제의식이었다. 문서는
역할·섹터·그룹·실질지역·자산종류·레버리지·통화 7개 축, 섹터 키워드 자동 제안·학습,
±10%p 밴드 판정, 단일 섹터/레버리지 한도, 조정 순서 안내, 분류 변경 이력, 시장
베타·상관 기반 역할 적정성 경고까지 포함한 상세 설계였다.

논의 결과 문서를 그대로 구현하지 않고, 이 앱의 기존 구조(단순함, 사용자가 직접 정의한
목표%를 실제%와 비교하는 것 하나가 핵심 가치)에 맞게 상당히 좁힌 버전으로 합의했다.

## Decision

**정확히 2개의 분류 축만 도입한다: 역할(고정 5개)과 섹터(자유, 역할에 종속).** 시장
(실질지역, ADR-0058)은 변경 없이 유지한다. 그 외 문서의 그룹·자동화·밴드·한도·이력·
측정값 축/기능은 **전부 이번 범위에서 제외**한다.

- **역할** — "왜 샀나". 성장/방어/인컴/헤지/현금성 5개 고정, `holdings.role` 컬럼
  (nullable text + CHECK, `AssetType`과 같은 패턴 — 별도 테이블 없음). 목표%는 총자산
  기준으로 반드시 100% 합계(기존 시장 축과 같은 규칙), `axis_targets`에 `axis: 'role'`로
  저장해 기존 인프라(`saveAxisTargets`/`targetsByBucket`/`useAxisTargets`)를 그대로
  재사용한다.
  - 5번째 카테고리는 사용자가 이미 만들어 쓰던 "역할기반" 탭의 "원자재"가 아니라
    **"헤지"**로 확정했다 — "원자재"는 "왜 샀나"가 아니라 "무엇인가"를 답하는 섹터
    성격의 라벨이라 섹터 축과 개념이 겹치고, 문서 자체도 원자재 ETF(PICK/REMX/SIVR)를
    "성장 역할 + 원자재 섹터"로 분류하면서 SIVR엔 "폭락장 헤지 기준 미충족"이라는
    메모까지 남겨 헤지를 실제로 검토했던 흔적이 있었다. 이 앱의 신한 인버스 200 ETN
    (530011, 주식 폭락 때 오르는 구조)이 헤지 역할의 실제 사례다.
- **섹터** — "무엇에 베팅하려고 샀나". 사용자가 계속 새로 만들 수 있는 목록, `sectors`
  테이블(id/user_id/name/target_pct/sort_order — 옛 `asset_groups`와 같은 패턴) +
  `holdings.sector_id` FK. **화면상 항상 어떤 역할 버킷 "안에서"만 나타난다** — 섹터
  하나가 여러 역할에 동시에 걸치는 경우는 드물다고 보고 신경 쓰지 않는다. `target_pct`는
  "그 섹터가 속한 역할 버킷 내에서의 목표%"로 해석하고, **역할과 달리 100% 합계를
  강제하지 않는다**(느슨한 참고용 — 미지정 종목이 남는 것도 이 앱의 기존 원칙,
  ADR-0059와 같은 정신). 섹터 목록은 **빈 상태로 시작**한다 — 문서의 13개 섹터
  프리셋을 미리 심지 않고, 매매/재분류하면서 사용자가 하나씩 만든다.
- **종목 하나는 역할 하나·섹터 하나만 가지므로 N:M 매핑 테이블이 아니라 `holdings`의
  직접 컬럼으로 저장한다.** 이게 이번 결정의 핵심 아키텍처 차이다 — 커스텀 탭 시스템은
  "한 종목이 여러 탭에 각각 다른 버킷으로 배정될 수 있다"는 N:M 관계라 별도 매핑
  테이블(`custom_tab_holding_buckets`)이 필요했지만, 역할·섹터는 종목의 고정 속성이라
  `asset_type`/옛 `group_id`와 같은 단순 컬럼으로 충분하다.
- **분류 입력은 매매 시점(매매 모달)이 기본** — 새 종목을 등록하면서 역할 칩 5개 +
  섹터 콤보박스(검색, 없으면 "+ 새 섹터 만들기"로 그 자리에서 생성)로 바로 채운다.
  **`/holdings`에서도 언제든 바꿀 수 있다**(기존 종목 편집 다이얼로그에 같은 필드
  추가). 매매 모달에서 기존 종목을 고르면 현재 역할·섹터를 칩으로 보여주고 "변경"
  링크로 다시 고를 수 있다 — 매매 저장과 무관하게 즉시 반영된다.
- **레버리지**는 `holdings.leverage`(기본 1) 컬럼으로 추가하지만, **비중·한도 계산에
  전혀 쓰지 않는 순수 표시용 메타데이터**다. 문서는 "레버리지 명목노출(Σ평가금액×배수)"
  한도 개념을 제안했지만, 사용자가 "비중 계산에서 배수를 곱할 필요는 없다"고 명시적으로
  판단해 뺐다.
- **`/portfolio`는 역할/시장 2개 고정 탭**(더 이상 유저가 탭을 만들거나 순서를 바꾸지
  않는다). 섹터는 별도 탭이 아니라 **역할 버킷을 펼쳤을 때 내부가 다시 섹터별로 중첩돼
  보이는 구조**다(성장뿐 아니라 방어·인컴·헤지·현금성 전부 동일 — 섹터가 어느 역할
  버킷에 나타날지 미리 알 수 없으므로 모든 역할이 똑같이 섹터로 쪼개진다). 드래그 배정
  UI는 없다 — 분류는 매매 모달/`/holdings`에서 입력하고, `/portfolio`는 비중 확인 +
  목표% 편집 전용이다(`RoleAllocationView`, `computeAxisRebalance`를 역할 레벨과
  섹터 레벨에 중첩으로 두 번 호출 — 계산 엔진 자체는 변경 없음).
- **`/holdings`의 필터는 축별 독립 필터**(지역/실질지역/역할/섹터/계좌, 서로 종속
  관계 없음)로 교체한다 — 옛 "포트폴리오(탭)+버킷" 2단 종속 셀렉트를 대체한다. 이
  화면의 필터는 비중 조절이 아니라 종목 조회·수익률 확인이 목적이라는 게 이번 논의로
  명확해졌다. 히트맵의 depth-1 그룹핑도 "선택된 탭"이 아니라 **역할**로 고정했다 —
  더 이상 "탭을 먼저 선택해야" 하는 제약이 없다.
- **커스텀 탭 시스템(`custom_tabs`/`custom_tab_buckets`/`custom_tab_holding_buckets`
  테이블, `TabEditor`/`TabBucketCard`/`TabHoldingRow`/`UnassignedHoldingsCard`
  컴포넌트, `useCustomTabs`/`lib/api/customTabs.ts`/`lib/portfolioTabDraft.ts`)는
  전부 폐기한다.** "역할기반" 탭의 배정을 `holdings.role`로, "원자재" 버킷 종목은
  "성장"으로 재배정한 뒤 이관하고, "자산군" 탭(13/67종목만 배정된 방치 상태)은
  이관 없이 삭제했다.

### 이번 범위에서 제외한 것 (문서엔 있었으나 안 함)

- **±10%p 밴드 판정**("조정 필요"/"밴드 내" 배지) — ADR-0056에서 이미 걷어냈던 유사한
  판정 시스템을 되살리는 것이라, 필요해지면 별도로 다시 논의한다.
- **섹터 키워드 자동 제안·학습, 분류 변경 이력 로그, 단일 섹터/레버리지 한도, 조정
  순서 안내** — 자동화·정책 계층은 핵심 분류 축(역할/섹터)이 자리잡은 뒤에 필요성을
  다시 판단한다.
- **그룹**(섹터 상위 묶음) 축 — 도입하지 않는다. 섹터가 이미 역할에 종속적으로만
  나타나는 구조라 한 단계 더 얹는 게 지금은 과하다고 판단했다.
- **시장 베타·주식 상관 기반 역할 적정성 경고("측정값")** — 이 앱은 정확히 같은 종류의
  파이프라인(Toss 캔들 페이지네이션+레이트리밋, 공분산/베타 계산)을 ADR-0058③(변동성
  축)에서 이미 한 번 만들었다가 "분류 기준이 안 정해졌다"는 이유로 되돌린 전례가 있다.
  핵심 축부터 끝내고, 필요하면 별도 후속 ADR로 다룬다.

## Consequences

- `holdings.role`/`sector_id`/`leverage`가 새로 생겼고, `sectors` 테이블이 생겼다.
  `axis_targets.axis` CHECK 제약이 `'market' | 'role'`로 바뀌었다(`'market'` 축의
  목표 편집 기능 자체는 그대로 유지 — 문서는 실질지역 축에 목표가 없다고 했지만 이
  앱은 이미 있던 기능이라 건드리지 않았다).
- 실 데이터 마이그레이션: "역할기반" 탭 배정 51종목 → `holdings.role`(성장 42·방어
  4·인컴 4·헤지 0·현금성 1), 역할 목표% 시드(성장30/방어25/인컴30/헤지5/현금성10 —
  사용자가 나중에 `/portfolio` 수정 화면에서 재조정할 값), 나머지 16종목은 미분류로
  남아 매매/편집 시 채워진다. `sectors`는 빈 테이블로 시작.
- **다음 기술부채로 남긴 것** (이번 마이그레이션과 무관한 더 오래된 항목이라 의도적으로
  같이 정리하지 않음, 역할/섹터 구현 완료 후 별도 후속 작업): `holdings.target_pct_in_group`
  컬럼 삭제(67종목 전부 0, 완전 미사용), `holdings.group_id` 컬럼 삭제(66/67이 값을
  갖고 있지만 앱 코드 어디서도 안 읽음), `holdings.sort_order` 컬럼 삭제(45/67이 0이
  아니지만 이미 SELECT조차 안 함), `asset_groups_deprecated` 테이블(15행) 삭제. 이
  네 항목을 정리할 때 group_id·자산군 계보를 다루는 ADR(0015/0016/0017/0018/0019/
  0035/0057/0059)의 Status를 "Superseded by ADR-00XX"로 갱신해야 한다.
- 매매 모달(`ExecutionFormDialog`)과 `/holdings` 편집(`HoldingFormDialog`)이
  `ClassificationFieldsBlock`(`components/shared/ClassificationFields.tsx`) 하나를
  공유한다 — 역할 칩·섹터 콤보박스(Korean-IME-safe, `useComboboxSearch`)·레버리지
  입력을 한 세트로 묶은 것. 섹터 콤보박스의 "+ 새 섹터 만들기"는 목표% 0으로 즉시
  생성한다.
