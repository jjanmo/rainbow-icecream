# ADR-0064: 종목별 매매 계획(정찰병·최대매수/분할·손절라인)과 보유 종목 행 색상 신호

## Status

Accepted

## Context

이 앱을 만든 목적은 시스템적·구조적으로 투자하는 것이다. 매수 근거(체결별 메모)만으로는
"이 종목에 얼마까지, 몇 번에 나눠 넣을지", "어디서 틀렸다고 인정하고 나올지"라는 계획이
남지 않는다. 그래서 매매일지를 적을 때 그 계획도 함께 적고, 보유 종목 표에서 계획 대비
지금 상태를 바로 알아볼 수 있어야 한다는 요청이 있었다.

## Decision

**계획은 체결(`executions`)이 아니라 종목(`holdings`)에 둔다** — 체결 한 건이 아니라 종목
하나의 계획이기 때문이다. 컬럼(전부 nullable, null = 계획 없음):

| 컬럼 | 의미 |
|---|---|
| `scout_amount` | 정찰병 최대 금액 |
| `max_buy_amount` / `split_count` | 최대 매수 금액 / 분할 횟수 — 표에는 `500만/5`로 표기 |
| `is_dca` / `max_undecided` | **적립식 / 최대 금액 미정 — 둘 중 하나만**(UI는 "최대 금액 지정 / 적립식 / 최대 금액 미정" 라디오 3택, 기본은 지정)(DB CHECK `holdings_plan_mode_check`, 사용자 결정: 적립식이면 최대 금액 개념이 없다고 본다). 어느 쪽이든 true면 위 두 값은 저장하지 않는다. 표기는 각각 `적립식`/`미정`. 처음엔 `max_unlimited` 하나였다가 "적립식인데 일정이 필요한 경우"와 "상한만 못 정한 경우"가 다른 입력을 필요로 해서 나눴다 — 기존 `max_unlimited = true` 6개 행은 rename으로 `is_dca`가 됐다 |
| `undecided_memo` | 최대 금액 미정일 때의 매수 전략 메모(자유 서술, 집계에 안 씀 — `trade_notes.body`와 같은 원칙). 미정이 아니면 null |
| `dca_frequency` / `dca_day` / `dca_amount` | 적립 일정 — `is_dca`일 때만 저장. 주기 `DAILY`/`WEEKLY`/`MONTHLY`(토스증권 "주식 모으기"와 같은 구분), `dca_day`는 매주면 요일(1=월…7=일)·매월이면 날짜(1~31)·매일이면 null, `dca_amount`(1회 금액, 원) / `dca_qty`(1회 주수, 소수 허용) 중 하나만 채운다(CHECK `holdings_dca_unit_check`, 입력은 금액/주수 라디오) — 단위 구분 컬럼 없이 어느 쪽이 채워졌는지로 판단. 전부 선택 — 적립식인데 일정을 안 정해도 된다. 표기: `적립식 (매월 25일 50만)` |
| `stop_loss_pct` | 손절라인 수익률(%) — 항상 음수(입력은 `-40`/`40` 둘 다 손실 쪽으로 해석) |

- **금액은 지역과 무관하게 항상 원화(KRW)**다 — 해외 종목도 계획은 원화로 세운다(사용자 요청,
  처음엔 종목 통화 기준이었다가 바꿨다). 입력은 만원 단위로 받고 DB에는 원 단위로 저장한다. 정찰병 판정 시 해외 종목의 투입 원가(`qty × avgPrice`, 달러)는
  실시간 환율로 원화 환산해 비교한다 — `/holdings` 표 하단 총 취득원가와 같은 환율·같은 성격의
  평가성 값이라 ADR-0038의 "환율은 평가금액에만, 실현손익엔 안 씀" 경계 안에 있다. 그래서 환율이
  움직이면 정찰병 미달 여부가 경계 근처에서 바뀔 수 있다.
- 입력 위치: 매매 모달의 "+ 새 종목" 블록과 기존 종목의 "변경" 링크(역할·섹터·레버리지와 같은
  인라인 편집, 즉시 저장 — 새 체결 추가뿐 아니라 **체결 수정 모드에서도** 보인다), 그리고 `/holdings` 종목 수정 모달. 세 곳 모두 `TradePlanFieldsBlock`
  (`components/shared/TradePlanFields.tsx`) 하나를 공유한다. 매매일지 종목 모드의 "매매 계획" 칸
  (`TradePlanCard`)에서도 근거와 함께 보고 그 자리에서 고칠 수 있다. 매수 근거는 기존 체결별 근거 메모
  (`trade_notes`)를 그대로 쓴다.
- `/holdings` 표는 **행 배경색 신호**를 보여준다(계획 값 자체를 보여주는 "매매 계획" 열은 한때 있었다가
  사용자 요청으로 뺐다 — 계획 확인·수정은 종목 수정 모달과 매매 모달 "변경" 요약에서)
  (`tradePlanSignal`, `lib/calc/tradePlan.ts`). 우선순위는 위험 신호가 먼저다:
  1. 빨강 — 수익률 ≤ 손절라인
  2. 노랑 — 수익률 ≤ 손절라인 + 10%p (예: 손절 -40%면 -30%부터)
  3. 하늘색 — 투입 원가 < 정찰병 금액. **평가금이 아니라 원가 기준**이다 — 주가가 빠졌다고
     이미 채운 정찰병이 다시 "미달"로 바뀌면 안 된다. 초록이 아니라 하늘색인 이유: 이 앱에서
     민트/초록(`GOOD_COLOR`)은 "좋음·목표 달성"인데, 이 신호는 "아직 할 일이 있음"이라 의미가 반대다.
- `/holdings` 필터 바 아래 **프리셋 칩**(`TradePlanPresetChips`)으로 "정찰병 미달"만 거를 수 있다(`TRADE_PLAN_PRESET_SIGNALS` — 손절 칩 2개도 만들었다가 사용자 요청으로 뺐다). 단일 선택 토글, 필터 바와 AND, 칩에 필터 바 적용 후 개수 표시, 칩 배경이 신호색이고 활성 여부는 테두리로만. **칩은 행 색상(최우선 신호 하나)이 아니라 조건 충족 여부로 거른다**(`tradePlanSignalsOf`가 걸린 신호 전부를 반환) — 처음엔 행 색상 신호로 걸러서, 정찰병 미달이면서 손절 경고인 종목이 칩에서 빠지는 버그가 있었다. 표 위 범례는 칩이 겸하게 하면서 없앴다.
- 계획이 없는 항목은 신호를 만들지 않는다 — 목표가 비어 있는 종목에 가짜 "매도 필요"가 뜨던
  ADR-0024의 문제를 반복하지 않기 위해서다. 이 계획은 리밸런싱 목표가 아니라 종목별 매매 계획이라
  ADR-0024(종목은 비중 목표를 갖지 않음)와 충돌하지 않는다 — 비중 계산(`computeRebalance`/
  `computeAxisRebalance`)에는 전혀 쓰지 않는다.

## Consequences

- 계획 변경 이력(특히 "최대 금액은 기업 성장에 따라 바뀔 수 있지만 근거가 필요하다")은 아직
  남기지 않는다 — 지금은 덮어쓰기다. 필요해지면 별도 이력 테이블로 확장한다.
- 최대 매수 금액 대비 채움률, "몇 번째 분할까지 샀는지", "수익률 n% 이하 추매 후보" 같은
  파생 신호는 이번 범위 밖이다 — 데이터는 이미 있으니 같은 `tradePlanSignal` 자리에서 확장할 수 있다.
