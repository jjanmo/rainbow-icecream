# ADR-0030: 금액·수량은 `number` 를 유지하고, 표현 오차는 반올림 경계 한 곳에서 봉쇄한다

## Status
Accepted (원본 설계의 Decimal 강제 결정을 이 프로젝트 맥락에서 뒤집음)

## Context

원본 설계는 금액·수량을 Decimal 라이브러리로 다루고 문자열로 저장하라고 했다. 근거는 실재한다: 소수점 해외주식을 다루면 전량 매도 후 보유 수량이 `0` 이 아니라 `2.8e-16` 으로 남고, "보유 없음" 판정이 실패하며, 그 잔량에 단가가 곱해져 유령 평가금이 생긴다.

그런데 이 프로젝트는 기존 계산(`lib/calc/rebalance.ts`, 시세·환율·평가금액) 전체가 `number` 다. 원장 도메인에만 Decimal 을 도입하면 경계마다 변환 계층이 생기고, 그 변환 자체가 새로운 오차·버그 지점이 된다.

## Decision

**`number` 를 유지한다.** 대신 원본 설계가 지적한 실패 모드를 두 지점에서 명시적으로 막는다.

- `roundCurrency(amount, currency)` — 통화별 반올림을 한 곳에 모은다. KRW 는 원 미만 절사, USD 는 소수 둘째 자리 반올림. **절사 전에 6자리로 한 번 접어 표현 오차를 걷어낸다.**
- `normalizeQty` / `isZeroQty` — 수량을 8자리로 정관화하고, 0 판정은 `QTY_EPSILON` 비교로 한다. 전량 매도 시 잔량·잔여원가를 명시적으로 `0` 으로 닫는다.

이 방어가 왜 필요한지는 검증 중에 실증됐다: `700000 * 0.00015` 는 IEEE754 에서 `104.99999999999999` 이고, 그대로 절사하면 수수료가 105원이 아니라 **104원**이 되어 취득원가가 1원 어긋났다. 사전 정관화로 해결했다.

## Consequences

- 기존 코드와 경계 변환이 없다. 번들도 늘지 않는다.
- **오차 방어가 `roundCurrency`/`normalizeQty` 를 통과하는지에 전적으로 의존한다.** 금액 계산을 이 함수들을 우회해서 하면 조용히 틀린다 — 새 계산을 추가할 때 반드시 통과시킬 것.
- 원본 설계가 금지한 epsilon 비교를 수량에 쓴다. 임계값이 코드 곳곳에 흩어지면 위험하므로 `QTY_EPSILON` 상수 하나로만 노출한다.
- 정밀도 요구가 커지면(예: 세무 신고용 정산) 이 결정을 다시 열어야 한다.

## 대안

- **decimal.js 도입(원안)**: 정확하지만 프로젝트 전체가 number 인 상태에서 경계 비용이 크다. 부분 도입은 최악.
- **정수 최소단위 저장**: 통화 단위가 섞이고 소수점 거래 문제가 그대로 남는다. 기각.
