# ADR-0051: 매매일지 보기 모드 — 달력/기간/종목, 종목 보기는 매수·매도 근거를 분리해서 표시

## Status
Partially superseded by ADR-0052 — 달력/기간이 하나로 합쳐졌다. 종목 모드와 그 근거 분리 표시는 그대로 유효하다.

## Context

매매일지는 지금까지 "달력에서 날짜를 골라 그날/그달 체결을 본다"는 한 가지 탐색 방식만 지원했다. 하지만 실제로 궁금한 건 종종 다른 축이다 — "최근 3개월 동안 뭘 샀지?"(기간), "이 종목을 지금까지 어떻게 사고팔았지, 그때 왜 그렇게 판단했지?"(종목). 지금 구조로는 종목 하나의 전체 이력을 보려면 달력을 한 달씩 넘겨가며 눈으로 찾아야 했다.

## Decision

**DB 스키마는 바꾸지 않는다.** `executions`에는 이미 `(holding_id, executed_at)`, `(user_id, executed_at)` 인덱스가 있고, `useExecutions()`/`useTradeNotes()`는 애초에 사용자의 체결·근거 전체를 필터 없이 한 번에 불러온다(페이지네이션 없음, RLS로만 스코핑) — 지금의 "이번 달 체결"도 서버에 다시 묻는 게 아니라 이미 받아온 전체 데이터를 클라이언트에서 날짜로 잘라 보여주는 것뿐이다. 기간별/종목별 보기는 이 데이터를 어떻게 묶어서 보여주느냐의 문제라, 새 쿼리나 새 테이블이 필요 없다.

**"보기 모드" 전환을 추가한다 (달력/기간/종목).** 달력을 없애지 않고 나란히 선택지로 둔다 — 날짜 기반 탐색은 이미 잘 맞는 UX라 바꿀 이유가 없다.

- **기간**: 프리셋(이번 달/최근 3개월/올해/전체) + 직접 지정(시작~종료 `type="date"` 입력) 중 하나로 임의 구간을 고른다. 그 구간의 체결·매수/매도/실현손익 합계·필터·표는 달력 모드와 같은 컴포넌트(`ExecutionsTable`, `ExecutionsFilterBar`, `TradeSummaryStrip`)를 재사용한다 — 새로 만든 건 구간을 고르는 UI와, 그 구간으로 좁힌 `periodExecutions`/`periodSummary`/`periodFxQuery`뿐이다. 과거 환율(`useHistoricalFxRates`)도 구간 전체를 한 번에 조회한다.
- **종목**: 종목 콤보박스(`ExecutionFormDialog`의 종목 선택과 같은 표기 규칙 — 해외는 티커 먼저)로 하나를 고르면, 날짜 제한 없이 그 종목의 **전체** 체결(기초잔고 포함)을 하나의 표에 보여준다. 달력·기간 모드와 달리 기초잔고를 제외하지 않는다 — 종목의 전체 역사를 보는 화면이라 시작점(기초잔고)이 빠지면 오히려 불완전하다. `ExecutionsTable`이 이미 날짜 없는 행을 대시로 표시하고 정렬에서 맨 앞에 두므로(ADR-0048) 그대로 재사용되고, 별도 표로 쪼개지 않는다. **매수/매도/실현손익 요약(`TradeSummaryStrip`)에도 기초잔고를 포함한다** — 기초잔고는 날짜가 없어 체결일 환율을 구할 수 없으므로, 그 몫만 `useExchangeRate`의 **오늘자 실시간 환율**로 환산한다(나머지 날짜 있는 체결은 그대로 `useHistoricalFxRates`의 체결일 환율). `holdingRateForExecution`이 `executedAt`이 없으면 실시간 환율을, 있으면 체결일 환율을 돌려주는 식으로 두 소스를 한 함수 안에서 분기한다 — 기초잔고를 요약에서 아예 빼는 대신, "환산 기준일이 다른 값이 섞인다"는 것을 감수하고 포함시키는 쪽을 택했다(사용자 피드백).

**종목 보기의 근거는 매수 | 매도 두 칸으로 분리한다.** 하나로 섞어서 시간순으로 보여주는 대신, 매수 근거와 매도 근거를 나란히 두 칸(`sm:grid-cols-2`)에 각각 시간순으로 나열한다 — 살 때의 판단과 팔 때의 판단은 성격이 달라서 섞어 놓으면 비교하기 어렵다는 피드백을 반영했다. 새 컴포넌트 `NotesColumn`과, `ExecutionFormDialog`의 `buyNotesFor`(매수만, 근거 있는 것만)를 일반화한 `notesForSide(executions, tradeNotes, side)` 헬퍼로 구현했다 — 후자는 매수/매도 어느 쪽이든 받는다.

## Consequences

- `/journal`의 데이터 로딩 방식(전체 체결·전체 근거를 한 번에 불러오는 것)은 그대로다 — 체결이 아주 많아지면(수천 건 이상) 이 방식이 부담될 수 있지만, 지금은 1인용 앱이고 기존 `replayHolding`도 같은 가정("종목당 체결 수백 건을 넘기 어렵다")을 깔고 있어 새로운 제약은 아니다. 데이터가 실제로 많아지면 서버 사이드 페이지네이션/필터링을 재검토해야 한다.
- 기간 모드의 "전체" 프리셋과 종목 모드의 FX 조회 범위는 모두 실제 데이터의 최초~최근 날짜(`dateRangeOf`)로 계산한다 — 프리셋을 누른 시점의 스냅샷이라, 그 뒤에 더 이른/늦은 날짜의 체결을 추가해도 "전체" 버튼을 다시 눌러야 반영된다.
- 달력 모드의 `monthSummary`/`daySummary`/`fxQuery`/`rateForExecution`은 건드리지 않고, 기간·종목 모드용으로 병렬 구조(`periodSummary`/`periodFxQuery`/`periodRateForExecution`, `holdingSummary`/`holdingFxQuery`/`holdingRateForExecution`)를 새로 추가했다 — 셋을 억지로 통합하기보다, 이미 검증된 달력 모드 로직을 건드리지 않는 쪽을 택했다.
- 종목 모드만 `useExchangeRate`(실시간 환율, 1분 폴링)를 새로 끌어온다 — 달력·기간 모드는 기초잔고를 아예 제외하므로 과거 환율(`useHistoricalFxRates`)만으로 충분했지만, 종목 모드는 기초잔고를 요약에 포함하기로 하면서 날짜 없는 행을 위한 별도 환율 소스가 필요해졌다. `/journal`이 종목 모드로 열려 있는 동안은 계속 폴링되므로, Toss 환율 API 호출이 그만큼 늘어난다(ADR-0005의 "1분 폴링" 정책 안에서는 문제없는 수준).
